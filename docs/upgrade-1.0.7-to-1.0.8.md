# 1.0.7 升级至 1.0.8 的批量购入与孵化检查

检查基准是仓库提交 `383ac81` 的已发布 1.0.7 代码。测试直接执行旧版建档与孵化函数生成数据，再交给新版处理，不使用生产账号。

## 已验证与修复

- 旧批量购入保留所有档案 ID、原始购入账本和图片地址，只在看板与账本选择器按批次显示。500 只不会再次创建 500 只，不新增收购账目。
- 旧版将总金额平均后逐只四舍五入，可能出现分币差额。新版仅对有完整关联、单价符合旧版统一舍入规则、没有手动改价证据的批次分配差额。收购总金额不变，原单价保存在 `legacyBatchUnitPrice`，处理标记避免重复分配。缺失成员或改过单价的记录不擅自调整。
- 旧孵化档案按已有孵化日期和品种分组，保留原 ID、日期、损耗与售出状态。新版有确认事件 ID 时仍逐次分组。旧版未存确认事件 ID，因此同日同品种的历史提交次数无法准确反推，不人为编造。
- 旧版只填写了累计孵化数、没有创建档案时，升级不会自动再增加孵化数。详情显示尚未关联的历史数量，提供补关联按钮，由用户选实际日期和品种；不填写或猜测旧版没有记录的信息。重复补关联不会创建重复档案。
- 旧累计数量 5 只，升级后本次孵化 2 只，累计为 7，只新增 2 只。旧的售出、损耗档案与关联事件仍占用历史孵化数量，不会作为缺失档案重新生成。
- 龟池旧手填数量未注明是否包含已关联档案，无法可靠自动推断。新版保留原数，对有歧义的旧龟池单独显示“已关联在养数量”和“历史手填数量”，不相加，也不冒充完整总数。编辑时可填写核对后的实际总数，程序减去已关联部分，余数记为额外未建档数量；保留 `legacyCount` 原值并标记 `countMode: additional`。只修改备注、数量留空时原数仍保留。新建龟池会明确标记额外数量，无需历史核对。
- 大批量请求复现了 UTF-8 字符跨网络分块时变成乱码的问题。服务器改为先合并原始字节再解码，并保留请求大小限制和中断处理。
- 新数据经过旧版正常读取和保存后，批次标识、分币信息、孵化事件及账本数据仍保留。保持服务端最低版本 95、公开版本 99，不改变 1.0.7 原有接口合同。新旧端同时编辑同一记录仍需并发保护，旧客户端本身没有新版版本校验能力。

## 验证

- `node scripts/test-version-upgrade.js`：旧版生成数据、金额、数量、分日孵化、历史补关联、售出损耗、重复迁移与旧客户端往返。
- `node scripts/test-version-upgrade-ui.js`：390px 手机页面、500 只批次选择、补关联后继续孵化、重载后数量与龟池。
- `node scripts/test-json-request-encoding.js`：中文与 emoji 按 1/2/7/1024 字节分块、大小限制、中断请求。
- `node scripts/test-api-workflows.js`：真实隔离 API 的旧版上传 → 新版修改保存 → 旧版再次保存 → 再次读取逐字段比较。
- 批次、损耗、孵化及同步的已有相关回归测试继续运行。

浏览器测试需要设置 `PLAYWRIGHT_MODULE` 和 `BROWSER_EXECUTABLE`；历史生成器需要包含 `383ac81` 的 Git 历史。此次本地仍为 1.0.8（104），未部署服务器或生成签名 iOS 包。真实 iPhone 保留旧 App 数据后覆盖安装新版的验收仍需在发布前进行。
