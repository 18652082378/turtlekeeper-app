## 正式环境发现的未解决差距

公开 Web 首页仍声明 build 109，而公开版本接口要求最低 117、最新 119。除 HTTP 探测外，本轮也在浏览器实际打开正式首页，看到“需要更新后才能继续使用”弹窗与 109/119 版本信息；该公开网页入口因此无法正常进入功能页面。

公开 `care-records.js`、`ui-system.css`、`ui-experience.js` 返回 404；Web 版本查询仍返回 iOS 更新门槛，版本接口未带当前本地实现预期的禁止缓存头。需要核对正式静态资源发布与平台版本策略。本轮没有可用的服务器运维连接或已核对的正式服务器制品，因此未覆盖线上文件。

这些观察针对正式域名提供的网页，**不能推断 App Store 已安装包的内置资源也为 109**，也不能推断服务端没有养护修复。上面的正式养护 API 保存验收实际上已通过。

证据：[正式只读探测](../output/release-acceptance/production-readonly.md)。HTTPS 与已知 HTTP→HTTPS 跳转正常；这不代替数据库健康、备份或运行源码核对。

- 客户端保存、删除、会话和恢复竞态：23/23。

**断网边界：**Windows WebKit 的整体离线开关会使主文档重载失败，使用无应用代码的最小页面也复现。因此 WebKit 数据矩阵保留测试用本地静态资源，阻断所有 API，模拟网络状态与事件，实际重载文档并核对待同步日志，随后恢复连接。这验证内置静态资源场景下的数据恢复逻辑，不等于普通网页完全离线可用或 iPhone 飞行模式测试。Chromium 的既有测试使用其整体离线开关。
