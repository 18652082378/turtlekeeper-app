第一步提示上传成功后，在服务器终端执行：


若提示 `Server source has local changes`，说明尚未安装或重启。先执行以下只读检查，取得文件名、改动规模及当前提交，再判断如何保留或合并服务器修改：

```bash

cd /www/turtlekeeper-app || exit 1
git log -1 --format='%h %s'
git status --short --untracked-files=no
git diff --stat
git diff --cached --stat

```

这些检查不会输出文件正文、清理修改或重启服务。未确定服务器本地修改的用途前，不通过强制重置或自动隐藏全部修改来绕过检查。

服务器脚本会核对版本、Node.js 22+、目标 PM2 进程和干净的代码目录；在当前登录用户的 `$HOME/.turtlekeeper-release-backups` 保存上一版本已提交源码，再快进更新代码、安装生产依赖、检查语法、重启 `turtlekeeper-api` 并验证公开版本接口。备份位于用户私有目录，避免要求该用户对项目父目录 `/www` 具有写权限。

不会修改现有 `.env`、用户数据库、上传目录或密钥，不执行数据库迁移，不提高旧版 App 的最低可用构建号。源码备份不替代用户数据库备份。若服务器已有本地代码修改或 Git 历史分叉，脚本会停止并保留文件，不使用 `reset --hard`。如果部署后就绪检查失败，脚本会报错并显示源码备份位置，不声称部署成功。

本轮服务器配置仍按现有商店最低版本运行。不要在 137 尚未上架时把 `MIN_SUPPORTED_APP_BUILD` 调高到 137，以免旧版用户被要求更新到尚不可下载的版本。

安装器只接受本次已核对的 7 个文件和 9 处冲突。它在私有临时目录做三方合并，采用已核对的 137 片段，并允许移除旧护理补丁的重复原始字段及注释标记；若仍有其他差异，会输出差异并停止，尚未更改运行代码。

核对通过后，安装器另存 7 个实际工作文件、二进制差异及旧提交号，再将这 7 个已核对文件保存为可恢复的 Git stash，调用常规部署脚本快进到同一已核对提交。它拒绝未核对文件改动、暂存修改、进程自动监视及发布提交变化。旧 Git stash 作为备份保留，不要将其应用到 137 上。

若旧服务器手动放置过尚未被 Git 跟踪的代码（如 `assets/team-space.css`），安装器会一次检查所有与新版路径重合的文件。只有内容与新版或新版 Git 历史中的版本一致，才列入可升级清单：文本允许 CRLF/LF 差异，二进制文件必须逐字节一致。所有无法识别的文件会一起列出并停止，运行代码尚未修改。公开 CSS 已只读比对，确认为历史提交 `55636e6` 的版本。

应用时先将已识别的未跟踪文件复制到私有备份的 `untracked-source/`，验证副本并记录原始校验值、文件权限和匹配提交；再次确认源文件未变化后，才清除这些冲突路径并立即让 Git 安装新版。若快进之前失败，会恢复这些旧文件；若文件被其他操作改写，保留并发修改并提示从备份恢复。不处理新版路径之外的未跟踪文件，不清理整个工作目录。

如果快进之前失败，安装器尝试恢复旧工作文件；若已经快进但安装依赖或就绪验证失败，会报告失败和备份位置，不自动宣称回滚完成。不会改写环境文件、数据库或上传文件。
