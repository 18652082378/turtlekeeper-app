# 两台设备的售出和损耗记录不一致

## 107 同步页操作入口

- 同步、核对、确认、导入、导出和重试备份统一使用当前应用根节点的事件委托，避免恢复页面节点后丢失绑定，并让本地存储告警和设置页的两个导出按钮都可用。
- 同步页显示持续的操作状态。账号读取/保存请求在 20 秒后中止等待并允许重试；保存超时不清除待同步日志，服务器可能已经提交的情况仍通过版本和完整数据核对处理。
- 用户主动打开差异列表会明确刷新，不再受返回页面的短暂渲染保护阻挡。读取过程中离开页面不强制跳回同步页。
- 文件选择保持在点击手势内调用，导出文件准备异常会反馈；备份不受网络等待阻挡。

新增 `node scripts/test-sync-actions.js`：以移动视口和触摸输入，从空间真实点击进入同步页，验证立即同步、查看差异、返回再进入、无逐节点监听器的页面恢复、两个导出入口、文件选择、无效导入、iOS 导出桥接的保存/取消结果、超时与断网重试，以及确认后恢复同步。iOS 文件保存使用桥接替身，不能冒充真实 iPhone 系统文件窗口验收。

## 105 手机显示同步已暂停时，电脑改价没有更新

2026-09-12 用户确认手机为 1.0.8（105），回到前台等待后仍显示“同步已暂停，本机修改已保留”。该状态会阻止自动上传及后台读取；服务器启用分记录存储不会清除客户端待同步日志，也不会更新安装包中的代码。

处理必须保留手机待同步数据。当前源码提供应用内逐组核对入口，但已安装的 105 需要安装包含该修复的新构建才可使用；不能通过清缓存、卸载或直接采用云端覆盖来冒充恢复。冲突核对现在也显示档案购入价，便于区分两端金额。服务器保留原来的 1.0.7 支持门槛。

`scripts/test-sync-two-devices.js` 增加改价表单到另一端刷新、旧版无共同基准的暂停日志升级、确认前保存双方原始价格、处理后重启及继续改价同步的回归场景。测试通过本地 API 和两个浏览器运行，不能替代用户手机上的最终验证。

## 普通用户的处理方式

从此次修改开始，客户端保存上次成功同步的完整基准快照，并将基准与待同步内容一起写入本机日志。收到其他设备的新版本时，比较基准、本机和云端，按记录 ID 汇总独立修改。比如电脑断网售出 A、手机断网损耗 B，联网后两笔操作及其关联成本和档案状态一起保留，无需导出或人工修复。

同一条记录的不同修改、删除与更新相撞、重复编号、龟池删除与新关联、同窝孵化数量冲突等不能凭时间猜测。此时提示只出现一次，用户点“查看并处理”，在应用内查看每组关联档案、账本、数量和金额，选择本机或云端这组记录后确认。有关联的数量、成本和孵化档案作为一组处理；保留两端成长历史。没有共同基准的旧版数据也使用这个入口，不要求普通用户导出 JSON 找技术人员。

冲突组的选择会采用所选端的这一整组关联记录，不能宣称所有同时发生的批次操作都能自动叠加。两端原始副本在确认前持久化；核对时本机变化或服务器版本变化会重新核对或拒绝旧写入。原始备份导出和已核对文件导入放在“备份与高级恢复”中，作为排障工具。

代码更新需要进入每个客户端后生效。服务器接口和 1.0.7 兼容门槛没有变化；旧版客户端自身不具备新客户端的基准比较和冲突界面，不能声称混用旧版时也获得完全相同的保护。

验证：`node scripts/test-account-merge.js` 覆盖独立售出/损耗、成本幂等、删除/更新、重复编号、龟池关联、孵化限制、成长历史保留和万只批次；`node scripts/test-sync-two-devices.js` 使用真实临时 API 和两个浏览器验证断网双端售出/损耗自动汇总、独立支出自动汇总，以及手机内完成真实冲突处理，不依赖任何恢复文件。

## 已修复的问题

- 图片上传完成后仅替换当前记录中的图片地址，不再用上传前的档案、账本副本覆盖上传期间新增的损耗或售出。
- 保存回执只清除该次提交对应的待同步数据；上传期间的新修改继续保留。
- 启动时不再按两台机器的时间戳丢弃待同步记录。遇到冲突保留本机数据，并提示导出核对。
- 账号在看板、账本、空间、同步设置页面空闲时每 30 秒拉取更新，回到应用或恢复网络时也尝试读取。编辑或有待同步修改时暂停后台覆盖。
- 同步设置的按钮接通保存、读取流程，提供本机完整 JSON 备份导出。补上之前遗漏的 `sync` 页面路由，并在空间加入“数据同步与备份”入口。
- 账号读取与保存回执返回 `updatedAt`，修复之前客户端始终取得空版本、导致正常保存也被拒绝的问题。接口测试必须断言该字段实际存在，不能把 `undefined` 当作有效版本传回服务器。
- 新客户端优先提交 `baseDataRevision`，仅账号资料及业务数据变化时版本改变。注册通知设备等操作不再造成账本冲突。服务器保留 `baseUpdatedAt` 回退和不带版本字段的 1.0.7 请求兼容；旧客户端尚不具备这项冲突保护。
- 切页、未读数和其他不改变账号保存内容的状态更新，不再创建待同步记录或触发账号保存。
- 遇到真实冲突后暂停自动重试，暂停状态写入本机备份与待同步记录。相同冲突只提醒一次；看板、账本、空间保留同步设置入口。手动同步可重新核对。
- 完整同步内容与云端一致时，可自动确认旧待同步记录、恢复有效版本和同步。仅报表金额相同不足以清除待同步记录；内容有差异时按共同基准比较独立修改，不能自动选一端覆盖另一端。
- 恢复网络、回到应用及定时检查时先补传待同步记录，再读取云端；首次启动读取失败后允许自动重试，不再卡在初始化已开始状态。补传不要求用户离开当前模块，刷新画面仍避开正在编辑的表单。
- 启动读取先检查并保留本机待同步数据，再决定是否显示云端。不会先渲染云端再恢复本机，也不会重建未变化的表单、重置已暂停状态或重新弹出同一冲突提醒。
- 同步设置增加“导入已核对的恢复文件”。文件同时包含两份原始快照和已核对的恢复结果；普通单端备份不能直接覆盖账号。当前本机、当前云端必须逐字段匹配其中一份原始快照或恢复结果，否则停止。显示恢复数量和金额，经用户确认后，先验证恢复前副本已写入本机存储，再使用云端数据版本进行条件保存。另一端导入同一文件时，若云端已是恢复结果，仅恢复本机，不再次上传。
- 导入期间新增的本机修改保持原版本及待同步记录；云端版本发生变化时拒绝写入。保存回执丢失后可重试，已完成的恢复不会重复入账。

## 已经分散在设备上的记录

修复代码不能凭空找回已被覆盖的记录，也不能只凭同一个手机号确定哪份完整快照正确。先在两端账本选择全部日期，确认是否是日期筛选。保留两端本地缓存和待同步数据；核对各设备的完整备份，以及服务器账户恢复快照或每日备份。

比较时按记录 ID 核对，不能仅按金额去重。损耗的成本转移、关联档案、收购剩余金额及撤销快照需要一起核对，不能只拼接账本数组。实际合并应先生成可审核的恢复结果，再写回账号。

本地仓库里的修改不会自动进入已安装的客户端；更新网页及原生客户端后才有新的恢复入口。此次修复保持本地 1.0.8（105）及生产环境最低版本门槛不变，没有新增服务端接口。已提交过的原生构建不能靠推送 Git 自动更新。
